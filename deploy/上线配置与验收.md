# KTV 上线配置与验收

本地功能开发与第三方真实交易验收是两个步骤。当前可以运行顾客、食堂、移动管理和 PC 运营流程；正式微信账号和 HTTPS 域名由项目方后续提供。未配置时，微信登录、小程序码和真实支付接口返回明确的不可用状态，不能用演示付款代替上线验收。

## 启动与迁移

1. 新建独立 MySQL 8 数据库及限定权限账号，准备 Redis。仅在**空数据库**导入 `sql/init.sql`；该文件包含 DROP TABLE，已有数据库不得重复执行。
2. 按 README 的 `BootstrapSystemAdmin` 指南初始化 PC 管理员。移动管理员和首个食堂密码仅用于首次初始化，至少12字符且 UTF-8编码不超过72字节。密码、数据库凭据、证书私钥不放入前端或 Git。
3. 复制 `application-production.example.yml` 到仓库以外的配置目录，设置其中环境变量；`JWT_SECRET` 使用足够长的随机值。首次启动需要两项移动账号初始密码。
4. 构建 `mvn -pl ruoyi-admin -am clean verify`，运行 `java -Xms256m -Xmx768m -jar ruoyi-admin/target/ruoyi-admin.jar --spring.config.additional-location=file:/etc/ktv/application-production.yml`。Windows 使用实际的 `file:C:/...` 地址。
5. 升级前停止旧版 API，使用 `mysqldump --defaults-extra-file=/安全目录/mysql-client.cnf --single-transaction 数据库名` 备份数据库，并备份 `KTV_UPLOAD_PATH` 和 `RUOYI_UPLOAD_PATH`。密码写入受限权限的 MySQL 客户端配置，勿放命令行参数。
6. 新版启动自动创建 `ktv_order`、`ktv_identity`、`ktv_payment`、`ktv_audit`、`ktv_qr`、`ktv_rate` 等表；将旧 `ktv_shared_state.orders` 在一个事务中迁移到独立订单表，并记录 `schemaVersion=2`。餐品、包厢、账号和原订单 ID、金额、事件均保留。同时为已有订单表补充 `room` 列并分批回填，用于历史包厢筛选；中断后可继续回填。迁移可重复执行。**不要混跑旧版和新版实例。**
7. 回滚时停止新版，恢复同一时点的数据库与上传备份后再启动对应旧版。先在独立数据库演练恢复，不可直接覆盖正在营业的数据。切勿只回滚 Jar 而保留新表结构中的业务数据。

## 微信配置

| 环境变量 | 内容 |
| --- | --- |
| `KTV_CUSTOMER_URL` | 顾客 H5 入口，例如 `https://order.example.com/#/pages/index/index` |
| `KTV_PUBLIC_API_URL` | 公网 API 根地址，例如 `https://api.example.com`，末尾不加 `/` |
| `KTV_ALLOWED_ORIGINS` | 允许的 H5/PC 来源，逗号分隔，不使用 `*` |
| `KTV_WECHAT_APP_ID` | 已认证小程序 AppID；与客户端 `manifest.json` 一致 |
| `KTV_WECHAT_APP_SECRET` | 小程序 AppSecret，仅服务端保存 |
| `KTV_WECHAT_MERCHANT_ID` | 与 AppID 绑定的微信支付商户号 |
| `KTV_WECHAT_PRIVATE_KEY_PATH` | 商户 API 私钥的绝对路径 |
| `KTV_WECHAT_SERIAL_NUMBER` | 商户 API 证书序列号 |
| `KTV_WECHAT_PUBLIC_KEY_PATH` | 微信支付平台公钥文件的绝对路径 |
| `KTV_WECHAT_PUBLIC_KEY_ID` | 与平台公钥匹配的公钥 ID |
| `KTV_WECHAT_API_V3_KEY` | APIv3 密钥，仅服务端保存 |

本实现使用微信支付官方 Java SDK 0.2.17 的公钥模式，不能把商户公钥误填成微信支付平台公钥。证书与密钥文件需限制读取权限；轮换后重启服务并执行查单/回调验签回归。

小程序的 `request`、`uploadFile`、`downloadFile` 合法域名配置为实际 API HTTPS 域名，保持 `manifest.json` 的 `urlCheck=true`。构建客户端前设置 `VITE_KTV_API_ORIGIN`。小程序码页面为 `pages/index/index`，正式生成前该路径必须已经发布。小程序码 scene 为服务端生成的32位随机值；重生成码后旧码失效。

支付通知地址为 `/ktv-api/wechat/payment-notify`，退款通知为 `/ktv-api/wechat/refund-notify`。反向代理必须保留原始报文和 `Wechatpay-*` 头，不能重新序列化 JSON。数据库保存唯一业务支付单号、微信交易号和退款单号；SDK 验签解密后校验商户、AppID、付款人和金额。重复通知不重复出单/退款。前端支付组件返回成功后仍以服务端查单结果为准。

H5 可扫码选餐和运营联调；真实付款入口当前是微信小程序 JSAPI。不要把 H5 评审面板当成已开通的微信 H5 支付产品。

## 业务规则与运行

- 订单按服务器价格计算，保留成交快照；每个顾客最多5笔待付款订单。请求幂等键防止重复创建。
- 默认15分钟未付款自动关单；可通过 `ktv.unpaid-timeout-minutes` 配置，`0` 表示关闭超时取消。每分钟核对未确认支付和处理中的退款。第三方请求失败保留原单据编号，后续重试不新建付款或退款编号。
- 顾客可取消未付款订单。真实已付款订单由管理员填写原因后申请**全额原路退款**；没有自动部分退款、营销或分账。退款处理中暂停食堂推进状态。异常退款需到商户平台核实，不能通过手工改本地状态假装退款成功。
- 新订单分配给首个启用且具有接单、送达权限的食堂；管理员可以填写原因转派进行中订单。食堂仍有进行中订单时不能停用或撤去处理权限。
- 食堂确认出餐必须逐项核对餐品。顾客订单通过小程序 OpenID 或 H5 本地恢复凭据保留；H5 清空全部浏览器数据后不能自动证明旧访客身份。
- 历史订单每页100笔，详情可单独读取；订单号/包厢搜索、状态和付款条件在后端对有权限的全部历史订单筛选，再分页；食堂待接单提醒与总数独立于当前筛选页。后台写入记录操作者、对象、原因、前后状态及请求编号。日志不记录密码和令牌。
- `ktv.production=true` 禁止开启演示支付。演示模式只用于隔离测试库。前台声音提醒仅在应用前台工作；后台推送不在当前功能范围内。
- 上传目录与数据库一起备份，不能使用临时目录。仅上传 PNG/JPEG，服务端检查尺寸后重新编码。未引用图片暂不自动删除，避免误删历史订单引用资源；定期核对备份与存储容量。

## 部署与验收

`deploy/nginx.conf.example` 提供三个 HTTPS 域名的反向代理示例。替换域名、证书、静态目录后运行 `nginx -t`。H5 静态目录使用 `ktv-app/dist/build/h5`，PC 使用 `ktv-admin/dist`。不要对外暴露 Vite、源码目录、数据库、Redis、Swagger 或 Druid 控制台。生产日志级别用 info。

正式账号配置后须完成以下验收，记录真实微信交易号、退款单号和测试结果，但不要记录密钥：

1. 真机扫码识别正确包厢，旧码换码失效，停用包厢无法下单；微信登录换设备后历史订单一致。
2. 实际小额支付，验证顾客、食堂、移动管理、PC 同步；取消付款、断网、重复点击、支付回调延迟仍只有一笔订单。
3. 验证通知验签及重复通知、金额/付款人不匹配拒绝、主动查单补偿；确认在商户平台与本地金额一致。
4. 实际全额退款，断开 API 后恢复、重复申请、回调重放；确认资金到账且只有一笔退款。异常退款不能显示成功。
5. 完成接单、核餐、配送、送达；转派和停用保护生效；食堂不能访问其他食堂或顾客金额。
6. 账号停用、密码重置、退出后旧会话拒绝。部署前轮换历史开发凭据；原本曾位于前端 `.local` 的密码尤其需要轮换。
7. 在预估峰值下压测下单、状态轮询、图片上传；检查数据库锁等待、错误率、支付补偿日志。当前仍使用门店级短事务锁保证版本和分配一致性，多门店或高峰扩容需依据实际压测结果评估。
8. 在另一独立数据库演练备份恢复，核对订单总额、图片、账号与付款退款记录。测试通过后才切换真实营业流量。
