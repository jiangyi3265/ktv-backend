# 备货、缺货处理与接单通知

本功能面向单门店，沿用顾客先付款的流程。库存由备货人员核对实物，不自动扣减库存，也不会因缺货反馈直接扣款或退款。

## 业务流程

1. 顾客付款成功后，订单分配给有接单和配送权限的启用账号。
2. 备货人员在接单详情逐项核对餐品及数量，全部确认后点击「确认有货并接单」。旧客户端的接单接口保留兼容，新版本使用带版本校验的 `/accept`。
3. 缺货时选择餐品并填写说明，订单进入 `stock_issue`，暂停接单与配送。顾客可看到商家正在处理。
4. 商家查看缺货说明后，选择补货重派、转派或按现有微信全额退款流程处理。食堂无退款权限。补货与缺货转派后重新进入待接单；制作中或配送中的正常转派保留进度并提醒新负责人。
5. 出餐再次核对数量，然后配送、确认送达。状态由同一后端同步到各端。

## 通知启用

配置 `ktv.notifications.enabled=true`，并在受保护的服务器环境文件设置 `KTV_NOTIFICATION_ENCRYPTION_KEY` 为随机生成的 64 位十六进制值。生产配置示例已引用此环境变量；不要提交密钥到 Git，也不要随意更换，否则已有群地址无法解密。首次部署自动创建通知配置、绑定及发送队列表，不删除业务数据。

电脑后台「接单通知」分别列出商家与备货账号：

- 企业微信群：由群管理员添加群机器人，将 Webhook 地址填入对应账号配置。仅接受企业微信官方 HTTPS Webhook，AES-GCM 加密保存，不回显。让实际备货人加入群并开启群通知。群提醒无需逐单申请微信订阅权限。
- 微信订阅：先在公众平台添加适合当前服务类目的订阅模板，后台选择模板并映射字段。备货人员在小程序接单工作台点击「连接微信提醒」，再点击「授权接收微信提醒」；商家使用移动管理首页的相同入口。授权必须由本人点击。
- 已为本项目选择的「订单任务待处理提醒」映射为：`time1 → time`、`number2 → taskCount`、`thing3 → notice`。模板 ID 由当前小程序真实模板列表读取，不能复制其他小程序的 ID。
- 一次性订阅每次授权只可发送一条，用完需再授权。保持选择并不等于永久订阅。界面显示的是本地登记额度，最终以微信受理结果为准。每个业务账号绑定一个接收微信，更换人员后可解绑重绑。

新单提醒当前备货方；超过默认 5 分钟未接单提醒商家；缺货反馈提醒商家。前台声音提醒仍可使用，但不会在关闭小程序后持续响铃。

## 发送可靠性与权限

通知从已提交订单异步发现并保存到数据库，发送失败不回滚支付。事件按订单、接收账号、类型、分配轮次及渠道去重。发送前再次校验订单进度与当前负责人，失效事件取消。服务重启不会清空队列。

未配置或未授权显示「等待配置或授权」；微信 `43101` 要求重新订阅；明确的限流或临时错误有限重试。超时可能已送达，记录为「结果不确定」并停止自动重发，管理员核对后可手动重试。「已发送」仅代表渠道接受，不代表备货人已读或接单。

工作人员只能绑定自己的通知，顾客不能读取通知配置。仅管理员能配置群、模板、解除其他账号绑定和重试。通知不包含支付金额、顾客身份或微信交易号。密钥、OpenID 与群地址不返回前端配置列表。

## 验收边界

自动化覆盖有货确认、缺货暂停、权限及版本校验、补货重派、转派、退款状态、通知去重、额度消耗与重新授权、未知发送结果不自动重复、超时与缺货提醒。渠道调用使用测试替身，不作为真实人员已收到消息的证据。

上线后须由实际接单人员完成一次订阅授权或群配置，再用营业安排允许的真实订单确认：微信/群收到提醒、打开正确订单、缺货反馈后商家收到提醒。未经该步骤，不能声称后台提醒已经完整交付。所有支付写入自动化在隔离数据库执行，不在营业库制造已付款订单。
